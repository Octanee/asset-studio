# API Architecture

- **Style:** REST + JSON at `/api/v1`, OpenAPI 3.1 generated by FastAPI. The frontend client is **generated** from it (`openapi-typescript`), so types cannot drift. A contract test fails CI when the spec changes without the client being regenerated. Implemented in WP-06: `python -m asset_studio.openapi` writes `frontend/src/api/openapi.json`; `test_frontend_openapi_document_is_current` checks it against the code, and the frontend CI job regenerates `schema.ts` with `pnpm gen:api` and fails on any diff. Requests go through `openapi-fetch` (`frontend/src/api/client.ts`), which turns problem+json into `ApiError`.
- **Live updates:** Server-Sent Events at `/api/v1/events` (job progress, state transitions, engine status). The UI reconnects with `Last-Event-ID`. Implemented in WP-04 for job events (`event: job`, the id is the stored `job_event` id, so a reconnect replays what was missed; `follow=false` returns the backlog only).
- **Errors:** RFC 9457 problem+json with a stable `code` (e.g. `LIFECYCLE_TRANSITION_NOT_ALLOWED`, `MCP_NOT_ALLOWED`, `OVERWRITE_NOT_CONFIRMED`, `LICENCE_CONFIRMATION_REQUIRED`, `ENGINE_UNAVAILABLE`) and a localisable message key.
- **Idempotency:** POSTs that create jobs or publications accept an `Idempotency-Key` header (8–200 characters); MCP must send one (428 `IDEMPOTENCY_KEY_REQUIRED`). The first answer is stored for 24 hours and returned again for a repeat (`Idempotent-Replay: true`); the same key with a different request is 422 `IDEMPOTENCY_KEY_REUSED`. Implemented in WP-15 for `POST /generations`, `POST /versions/{id}:regenerate`, `POST /versions/{id}:process`, `POST /poses:detect` and `POST /publications`.
- **Long operations:** these always return `202` with a job id; there are no blocking calls.
- **Pagination:** cursor-based for lists such as the library, the audit log and jobs.

## Confirmations as data

Every confirmation the UI shows is enforced by the API, so MCP cannot skip it:
- overwrite (RULE-004);
- licence conflict (RULE-007);
- model download (RULE-008);
- permanent delete (RULE-019);
- SDXL training estimate (RULE-016);
- enabling `mcp_can_decide`.

A request without the explicit confirmation field fails with a problem code that tells the client what to confirm. For MCP, the high-impact confirmations — overwrite, permanent delete, `mcp_can_decide` — are **refused outright** and must be done by the user in the UI.
